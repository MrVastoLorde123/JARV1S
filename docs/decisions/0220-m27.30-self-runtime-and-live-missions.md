# Decision 0220 — M27.30 Self Runtime and Live Missions

## Decision
JARVIS should expose persistent runtime context as a spatial control layer rather than treating each space as an isolated page.

M27.30 introduces a persistent **LIVE MISSIONS** footer integrated with the existing Mission Spine. It is derived from the current snapshot and selected mission state, not synthetic activity. Selecting a mission updates the shared mission selection used by the workspace, Mission Control and mission flow surfaces.

SELF now acts as an internal **runtime environment** rather than a generic resource dashboard. It presents model fleet state, resource pressure, current operation and structured observations as coordinated lanes using the existing `JarvisSnapshot` contract.

The interface also expresses high-value runtime conditions globally. Connectivity, pressure, attention and operating mode are represented as document-level state attributes so individual surfaces can respond consistently without duplicating state logic.

## Why
The interface is intended to become the operator surface for JARVIS's eventual model workforce. The user must be able to see what work exists, what mission currently has focus, which stage is active, what model is associated, and where resource or authority boundaries apply without leaving the current space.

## LLM workforce implication
The UI must eventually represent real model orchestration primitives:

- model registry and capability profiles;
- routing and selection policy;
- task decomposition and delegation;
- temporary and persistent agents;
- context packaging and tool scope;
- resource-aware concurrency;
- result verification and comparison;
- fallback, retry and escalation;
- learning/evaluation signals separated from authority.

These are backend capabilities. The interface may visualize their structured state, but must not fabricate cognition or private chain-of-thought.

## Desktop shell
The current UI remains a Vite/React web interface so the presentation can iterate quickly and remain decoupled from backend/runtime services. A native shell can be added later without requiring a rewrite: the preferred architectural direction is a thin desktop wrapper around the same UI plus local JARVIS services, rather than moving authority into the GUI process.
