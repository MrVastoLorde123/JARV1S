# M28.14 — Browser HTTP World Transport

## Decision

Deliver the existing M28.13 `WorldObservation` / M11 `InterfaceResponse` to the browser through a minimal standard-library HTTP snapshot transport.

The concrete path is:

`backend world state → WorldObservationProjector → WorldObservation → WorldObservationInterfaceAdapter → InterfaceResponse → HTTP GET /api/world/observation → Vite /api proxy → browser world client`

## Why HTTP first

- The current backend has no web framework or identified HTTP/WebSocket server adapter.
- The repository does not require a new server dependency to expose a read-only snapshot.
- Browser-native `fetch` is sufficient for the first real delivery boundary.
- The payload remains the canonical M11 response, so transport can later change without redefining world semantics.
- Snapshot polling is deliberately preferred over prematurely inventing a second event protocol. A streaming transport can be added when backend event production exists and can use the same observation envelope.

## Transport contract

`src/interface/http_world.py` provides:

- `WorldObservationHTTPConfig` — host, port, endpoint, and CORS policy.
- `create_world_observation_server(...)` — creates a threaded standard-library HTTP server around an injected `WorldObservation` supplier.
- `serve_world_observation(...)` — blocking host-process entrypoint.
- `GET /api/world/observation` — returns one M11 `InterfaceResponse` containing the M28.13 world observation.
- `OPTIONS /api/world/observation` — browser preflight support.

The endpoint is read-only. It accepts optional request/session identity headers but exposes no command or authorization path.

## Frontend contract

`ui/src/worldObservationClient.ts` consumes the M11 response, verifies the `WORLD_OBSERVATION` payload marker and M28.13 schema, and parses the coherent world observation.

Vite proxies `/api/*` from the browser development host (`5173`) to the JARVIS transport (`8765`), avoiding browser-side hard-coded backend URLs.

## Boundaries retained

- HTTP is delivery only.
- `InterfaceResponse` remains the interface envelope.
- `WorldObservation` remains the backend world truth for rendering.
- No demo gateway state is promoted into backend truth.
- No UI control path is created by this milestone.
- No WebSocket/event-stream abstraction is introduced until there is actual backend event production to carry.

## Next consequence

The browser can now receive real JARVIS world state. The remaining integration work is to instantiate the HTTP server against the real backend `WorldObservation` producer and replace the relevant UI demo reads with this client. That is integration work, not another transport architecture decision.
