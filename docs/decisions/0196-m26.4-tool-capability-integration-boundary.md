# Decision 196 — M26.4 Tool Capability Integration Boundary

Status: IMPLEMENTED / VERIFIED LOCALLY

## Context

JARVIS already contains a provider-neutral capability registry, a tool registry/service, and a narrow `ToolCapabilityGateway` / `ToolInvoker` execution seam. These layers must remain distinct: capability declaration and discovery must not become authorization, while actual tool execution must remain explicit.

## Decision

M26.4 introduces `ToolCapabilityIntegrationBoundary` as the JARVIS-owned bridge between declared capabilities and the existing tool gateway.

The boundary SHALL:

- accept one injected implementation of the existing `ToolCapabilityGateway` contract;
- expose an immutable snapshot of the gateway's `ToolDefinition` values for capability discovery;
- translate tool definitions into provider-neutral `CapabilityDefinition` values without attaching executable behavior;
- register those declarations into an injected `CapabilityRegistry` only through the registry's existing contract;
- accept only exact `ToolRequest` values for invocation;
- delegate invocation to the existing `ToolCapabilityGateway` without modifying the request;
- accept only exact `ToolResult` values from the gateway;
- preserve the returned tool result and invocation identity as data;
- remain free of provider selection, authorization, confirmation decisions, persistence, truth semantics, certainty semantics, and model authority.

The integration boundary SHALL NOT infer permission from `RiskLevel`, `requires_confirmation`, or arbitrary metadata. Those remain declarations for later policy/confirmation layers.

## Data flow

```text
ToolDefinition
    ↓
ToolCapabilityIntegrationBoundary
    ↓
CapabilityDefinition → CapabilityRegistry

ToolRequest
    ↓
ToolCapabilityIntegrationBoundary
    ↓
ToolCapabilityGateway
    ↓
ToolResult
```

## Consequences

JARVIS gains one explicit seam for bringing real tools into its capability model without duplicating the existing tool contracts or allowing model output to execute implicitly. Discovery can become part of JARVIS's capability view while invocation remains a separate, explicit operation.
