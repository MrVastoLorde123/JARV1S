# M28.16 — Runtime World HTTP Host Bootstrap

## Decision

Wire the existing M28.14 browser transport into the real application process without creating another runtime, state store, or server architecture.

The host process now exposes a single opt-in bootstrap:

`JARVISRuntime → JARVISRuntime.observe_world → M28.14 HTTP server → browser`

## Host contract

`src/interface/world_host.py` provides `start_world_http(runtime)`.

It:

- requires the canonical `JARVISRuntime`;
- refuses to start when no real `AgentWorldRuntime` is configured;
- starts the existing standard-library M28.14 server on a daemon thread;
- returns a lifecycle handle for clean shutdown;
- owns no world state and performs no execution.

## Local launcher integration

`src/run_local_jarvis.py` recognizes `JARVIS_WORLD_HTTP=1|true|yes|on`.
When enabled, it starts the world host from the canonical runtime and closes it with the operator session.

The flag remains opt-in because the existing local launcher still does not construct a concrete M9 `WorkerRegistry` + `BoundedWorkerRuntime` world runtime by default. Starting the transport without that real producer would create a misleading empty/fake world path.

## Boundary retained

The application process is the owner of the transport lifecycle. `JARVISRuntime` remains the owner of the world observation composition. `AgentWorldRuntime` remains the owner of current runtime agent projections. M28.14 remains delivery only.

No UI state, mock agent, fake execution adapter, or secondary server was added to make the endpoint appear alive.

## Consequence

Host/process wiring is complete as a real integration seam. The remaining activation work is to configure the local application's existing M9 workforce/execution composition into `AgentWorldRuntime`; once that exists, the already-wired `JARVIS_WORLD_HTTP` path can expose the real world to the browser without further transport architecture changes.
