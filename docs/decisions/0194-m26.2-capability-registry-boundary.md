# Decision 194 — M26.2 Capability Registry Boundary

Status: IMPLEMENTED / PENDING LOCAL VERIFICATION

## Context

M26.1 introduced `JarvisRuntime` as the composition root for the verified M25 interface, activity, session, adapter, and orchestration path. JARVIS now needs an explicit description of what capabilities are available without coupling that registry to tool execution, model providers, authorization, or external side effects.

## Decision

M26.2 introduces `CapabilityRegistry` as a provider-neutral registry of immutable `CapabilityDefinition` descriptors.

The registry SHALL:

- identify capabilities by stable non-empty IDs and normalized names;
- retain human-readable description and category metadata;
- reject duplicate capability IDs and normalized names;
- expose immutable snapshots and direct lookup;
- preserve recursively frozen descriptor metadata;
- permit explicit registration and removal without invoking or inspecting capability implementations;
- remain independent of the existing tool execution gateway so real tools can be integrated later through a separate boundary;
- be composable by `JarvisRuntime` without changing M25 lifecycle semantics.

The registry SHALL NOT:

- execute capabilities or tools;
- authorize execution;
- select a capability for a request;
- define model/provider behavior;
- persist capability state;
- establish truth or certainty;
- mutate M24 lifecycle artifacts or authority state.

## Data flow

```text
Runtime composition
        ↓
CapabilityRegistry
        ↓
CapabilityDefinition snapshots

Future capability/tool boundary
        ↓
separate integration milestone
```

The registry is a catalog of declared capability identity and metadata. Registration is configuration of the runtime composition, not execution authority.

## Consequences

JARVIS gains an explicit answer to “what capabilities exist?” while keeping capability execution outside the registry. Future milestones can map tool implementations, plugins, model providers, or external services onto these declarations without making the registry itself an executor or authority layer.

## Verification

Local verification is pending. The focused suite will cover descriptor validation, duplicate rejection, normalization, recursive immutability, lookup/list snapshots, removal, runtime composition, and non-execution guarantees.
