# Decision 195 — M26.3 Model Provider Boundary

Status: IMPLEMENTED / PENDING LOCAL VERIFICATION

## Context

JARVIS already contains a provider-neutral `AIProvider` contract and AI request/response models. M26.1 and M26.2 established a runtime composition root and a capability registry, but no model may yet enter the core runtime as an implicit authority.

## Decision

M26.3 introduces `ModelProviderBoundary` and immutable `ModelSuggestion` as the narrow seam between an AI provider and JARVIS.

The boundary SHALL:

- accept one injected implementation of the existing `AIProvider` contract;
- build provider-neutral `AIRequest` values from explicit task/context inputs;
- validate the provider response as the existing `AIResponse` type;
- preserve provider, model, finish reason, usage, content, and metadata as a distinct immutable `ModelSuggestion`;
- recursively freeze returned suggestion metadata;
- expose provider identity without selecting or executing providers;
- permit `JarvisRuntime` to compose an optional model provider boundary without requiring one.

The model suggestion SHALL remain an observation/input to later deterministic JARVIS reasoning. It SHALL NOT authorize execution, execute capabilities, mutate state, persist state, establish truth, establish certainty, or become a lifecycle decision.

The boundary SHALL NOT define provider-specific communication, provider selection policy, tool execution, authorization, persistence, or model truth semantics.

## Data flow

```text
AIProvider
    ↓
ModelProviderBoundary
    ↓
ModelSuggestion
    ↓
future deterministic JARVIS reasoning / authority
```

The existing `AIProvider` remains the provider contract; M26.3 adds the JARVIS-owned boundary that constrains how provider output enters the system.

## Consequences

JARVIS can now use a local or remote model through a replaceable provider seam without making the model itself the system authority. Concrete providers such as Qwen, Phi, Ollama, Transformers, or remote APIs remain implementation choices for later integration work.

## Verification

Local verification is pending. The focused suite will cover provider contract validation, request construction, response preservation, recursive immutability, invalid input/output rejection, and non-authority guarantees.
