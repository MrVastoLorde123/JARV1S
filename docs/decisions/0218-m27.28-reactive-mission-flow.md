# M27.28 — Reactive Mission Flow

## Decision
Mission Flow is a state-reactive component, not a static orchestration illustration. HOME and the persistent Mission Spine derive their mission stage from the same presentation-safe mission flow state model.

## Contract
`deriveMissionFlowState(snapshot)` is the single presentation boundary for the five visible mission stages:

`OBSERVE → REASON → ASSIGN → EXECUTE → VERIFY`

The derived state contains:

- the current stage;
- overall operating status (`ACTIVE`, `STANDBY`, `ATTENTION`, `OFFLINE`, or `GUARDED`);
- a user-facing headline;
- the latest structured evidence available in the snapshot;
- the current guard condition;
- per-stage state and detail.

Stage selection is conservative. `Thinking` maps to `REASON`, `Learning` to `VERIFY`, and `Working` maps to `ASSIGN` only when the latest structured self-activity is `DELEGATING`; otherwise it maps to `EXECUTE`. Monitoring, waiting, and attention states remain observable without inventing hidden execution steps.

## UI integration
The existing HOME Mission Flow surface remains the spatial host, but its hard-coded FlowStep/FlowLine presentation is replaced by a React `MissionFlow` component mounted into that host. This preserves the existing layout while making the state itself component-driven.

Mission Spine consumes the same derived state so its stage indicator cannot drift from HOME.

## Guardrails
This layer is presentation-only. It does not execute work, infer private model reasoning, claim completed steps without evidence, or alter authority boundaries. Resource pressure and user attention are surfaced as operating conditions, not as fabricated cognitive activity.
