# Decision 198 — M26.6 Real Tool Capability Integration

Status: VERIFIED

## Context

M26.4 established the provider-neutral capability integration boundary, and
M26.5 established the guarded runtime-facing gateway backed by the existing
`PolicyGate`. The repository already contains a real harmless filesystem tool,
`ReadFileHandler`, which is read-only, LOW risk, workspace-confined, and returns
execution failures as `ToolResult` data.

V1 now needs evidence that an actual tool can cross the complete capability and
execution path without introducing a parallel safety mechanism or allowing a
model/capability declaration to execute directly.

## Decision

M26.6 introduces `RealReadFileCapability` as the first concrete V1 capability
composition. It wires the existing `ReadFileHandler` through the existing
production seams:

```text
ReadFileHandler
    ↓
ToolRegistry
    ↓
ToolService
    ↓
PolicyGate
    ↓
GuardedToolCapabilityGateway
    ↓
ToolCapabilityIntegrationBoundary
    ↓
CapabilityRegistry
```

The composition SHALL:

- construct the existing `ReadFileHandler` without reimplementing filesystem
  behavior;
- register the real handler through the existing `ToolRegistry` and
  `ToolService` stack;
- place `PolicyGate` between the capability boundary and the real handler;
- expose the real tool as a provider-neutral `CapabilityDefinition` through
  the existing capability registry;
- accept explicit `ToolRequest` values for invocation;
- preserve the request invocation identity in the resulting `ToolResult`;
- return routine tool failures as data rather than promoting them to authority;
- preserve the existing workspace containment enforced by `ReadFileHandler`;
- remain free of independent authorization, policy, execution, persistence,
  truth, certainty, and model authority.

Convenience `read()` construction is only request construction. It does not
bypass or replace `PolicyGate`, confirmation, authorization integrity, sandbox
admission, execution preparation, or execution attempt.

## Authority wall

```text
Explicit ToolRequest
        ↓
ToolCapabilityIntegrationBoundary
        ↓
GuardedToolCapabilityGateway
        ↓
PolicyGate
        ↓
Policy + Confirmation + Authorization
        ↓
Authorization Integrity
        ↓
Sandbox Admission
        ↓
Execution Preparation
        ↓
Execution Attempt
        ↓
ToolService
        ↓
ReadFileHandler
        ↓
Workspace
```

The real capability therefore crosses the same deterministic authority chain
used by the generic gateway contract. No model response is permitted to call
the handler directly.

## V1 scope

`read_file` is intentionally the first concrete tool because it is read-only,
LOW risk, and workspace-confined. This milestone proves the integration path;
it does not expand policy semantics or add a general tool orchestration engine.
Future tools may reuse the exact same stack.

## Consequences

JARVIS V1 now has a concrete, executable capability rather than only abstract
capability seams. The architecture has evidence that a real tool can be
registered, represented as a capability, explicitly invoked, authorization-
checked, sandbox-admitted, prepared, executed, and returned as structured
result data without collapsing capability into authority.
