# M27.22 — Lived Interface Signals and Containment

## Decision
JARVIS should feel continuously alive by surfacing meaningful system signals, not by cycling through synthetic cognitive states.

## Interface behavior
The persistent desktop layer may proactively surface a concise signal when canonical presentation-safe state provides a reason:

- user attention is required
- a request is being interpreted
- a project procedure is active
- learning/verification context is changing
- resource pressure affects posture
- otherwise, JARVIS remains quiet and ready

Dynamic telemetry may animate independently, but it must not imply cognitive work that has not occurred.

## Readability
The M27.19 readability step applies primarily to dense secondary text, descriptions, timestamps, status text and supporting metadata. Primary headings retain their existing visual hierarchy.

## Containment
Icons and textual values must remain inside their intended navigation/panel cells. Overflow should be clipped or elided instead of visually breaking the grid.

## Projects terminology
The user-facing WORK concept is presented as PROJECTS. Existing internal route identifiers may remain `WORK` until a deeper contract migration is justified.

## Light mode
Light mode is treated as its own material system. Correct selectors and explicit surface/border/text treatment are required; it is not a direct color inversion of dark mode.

## Boundary
These changes are presentation-only. They do not grant authority, execute capabilities, bypass policy, or reveal hidden model reasoning.
