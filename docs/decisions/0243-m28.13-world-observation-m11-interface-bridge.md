# M28.13 — World Observation M11 Interface Bridge

## Decision

Connect the backend `WorldObservation` to the existing canonical M11 interface boundary through a thin, transport-neutral adapter.

The adapter packages a read-only world observation as an existing `InterfaceResponse` payload. It does not introduce a second API, event bus, state store, authority surface, permission model, or execution path.

## Existing authority boundaries retained

- `WorldObservation` remains a read-only projection of backend agent/world state.
- `InterfaceBoundary` remains the canonical provider-neutral interface envelope.
- `InterfaceResponse` remains an output envelope and does not grant authority or authorize execution.
- A future HTTP, WebSocket, desktop, or other transport may carry the resulting M11 response without changing world semantics.
- UI code must not reconstruct world relationships from unrelated fragments when the coherent observation is available.

## Adapter contract

`WorldObservationInterfaceAdapter` provides:

1. `frame(...)` — wraps a concrete `WorldObservation` with request/session identity and optional metadata.
2. `response(...)` — serializes that frame and packages it through the existing `InterfaceBoundary.response(...)` contract.
3. `snapshot(...)` — convenience method for producing one read-only interface response from the current observation.

The serialized payload identifies itself as `m28.13.world_observation` and `WORLD_OBSERVATION` while retaining explicit non-authority markers.

## Why this boundary

M11 already defines the system's provider-neutral interface contract. Building another transport-facing abstraction would duplicate responsibility and make the world UI a parallel system instead of a surface over JARVIS.

The correct flow is:

`backend state → WorldObservationProjector → WorldObservation → M28.13 M11 adapter → InterfaceResponse → future transport → JARVIS World`

No network transport is created by this milestone.

## Consequence

The world frontend can now target the same canonical interface boundary used by the rest of JARVIS. Adding an actual transport later becomes a delivery concern rather than a new backend architecture decision.
