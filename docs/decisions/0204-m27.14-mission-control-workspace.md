# Decision 0204 — M27.14 Mission Control Workspace

**Status:** IMPLEMENTED ON `feature/m27.14-mission-control-workspace` / AWAITING LOCAL BUILD VERIFICATION

M27.14 continues interface-first development by turning the renderer into a unified JARVIS operating environment rather than a collection of unrelated dashboard pages.

## What changed

- Added a first-class **CONTROL** space for Mission Control and observable orchestration.
- Reworked navigation into **CORE** and **SYSTEM** groups with a quieter glass-black desktop treatment.
- Added a global command palette (`Ctrl/Cmd+K`) for rapid movement through the environment.
- Added persistent bottom status chrome for Core connection, session and runtime orientation.
- Connected **HOME → CONTROL → WORK → MIND → SELF** as related views of one operating system.
- Added a Mission Control pipeline: Context → Reason → Assign → Act → Verify.
- Added an inspector showing model assignment, decision summary, boundaries and next transition.
- Added a trace timeline using the gateway's current observable self-activity stream.
- Made Chat explicitly link back to orchestration rather than existing as an isolated chat page.

## Design direction

JARVIS should feel like a desktop command environment: glass-black surfaces, persistent spatial chrome, dense information hierarchy, quiet status indicators and purposeful motion. Blue is an accent, not the material.

## Orchestration visibility

The interface is deliberately designed around the fact that JARVIS is intended to coordinate multiple models, capabilities, projects, memory and tools. Future backend-backed records should be able to render:

- objective and scope
- selected context
- reasoning summaries and decision records
- model/agent assignment
- delegation and handoffs
- tool and capability activity
- evidence and source provenance
- verification and outcome
- blocked, waiting and user-approval states
- resource/concurrency decisions

The interface must not present fabricated private chain-of-thought as truth. It should display structured reasoning summaries and provenance that the backend intentionally exposes.

## Authority invariant

Mission Control is an observability and operator surface. It does not become execution authority. Backend validation, policy, authorization and execution boundaries remain authoritative.

## Entry point

`ui/src/main.tsx` now intentionally activates `App.tsx` and `mission.css` so the new interface is the renderer entry point for this branch.
