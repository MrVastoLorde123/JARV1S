# M27.24 — Temporal Signal Memory

## Decision
SIGNAL must have temporal behavior. A message that remains true every second is not a new message and should not be repeatedly treated as one.

The interface therefore keeps a small session-scoped ledger of signals it has already surfaced and uses that ledger when selecting the next presentation-safe signal.

## Behavior
- The selected signal remains visible for a short dwell period so the channel does not flicker between candidates.
- A signal is suppressed for a kind-specific interval after it has been surfaced.
- When the highest-priority signal has recently been surfaced, the next eligible candidate may be shown instead of repeating it immediately.
- A materially changed signal receives a new fingerprint and can be surfaced as new information.
- When all candidates are suppressed, the current highest-priority signal remains stable rather than manufacturing a new message.

## Memory boundary
This is presentation-session memory only. The ledger is stored in browser session storage and contains signal fingerprints and timestamps. It is not canonical JARVIS memory, learning state, intent, authority, or world-model state.

The temporal layer must never claim that JARVIS remembers the user, learned something, or changed its internal state merely because a signal was displayed.

## Truthfulness
Temporal memory may change when a message is presented, but it cannot change the underlying priority or meaning of the signal. Candidate generation remains owned by the presentation-safe signal prioritizer.

## Failure behavior
If browser session storage is unavailable or malformed, SIGNAL falls back to stateless prioritization. Storage failure must not block the interface or alter canonical runtime behavior.

## Boundary
M27.24 remains presentation-only. It does not execute actions, create authority, mutate canonical state, acknowledge user requests, or bypass policy and confirmation boundaries.
