# Decision 197 — M26.5 Guarded Tool Gateway Boundary

Status: VERIFIED

## Context

M26.4 established a JARVIS-owned integration boundary around the existing
`ToolCapabilityGateway`. The repository also already contains `PolicyGate`,
which composes policy, confirmation, explicit authorization, authorization
integrity, sandbox admission, execution preparation, and execution-attempt
boundaries before reaching `ToolService`.

A generic gateway contract alone does not prevent a future runtime composition
from wiring `ToolService` directly and bypassing those authority walls.

## Decision

M26.5 introduces `GuardedToolCapabilityGateway` as the runtime-facing adapter
for tool capabilities.

The adapter SHALL:

- accept only an exact existing `PolicyGate` instance;
- expose the gate's `ToolDefinition` values for capability discovery;
- accept only exact `ToolRequest` values for invocation;
- delegate invocation only to `PolicyGate.invoke()`;
- accept only exact `ToolResult` values from the gate;
- never expose or call `ToolService` directly;
- preserve request/result lineage as data, including normalized tool identity and `invocation_id`;
- remain free of independent policy, confirmation, authorization, persistence,
  truth, certainty, or model semantics.

The adapter SHALL NOT create a second authorization engine. The existing
`PolicyGate` remains the sole implementation of the complete guarded execution
sequence for this path.

The adapter SHALL NOT require Python object identity to survive the gate. The
existing `PolicyGate` may reconstruct the execution request from its immutable
handoff; semantic identity and invocation lineage must remain intact.

## Authority wall

```text
Capability / ToolRequest
        ↓
GuardedToolCapabilityGateway
        ↓
PolicyGate
        ↓
Policy + Confirmation + Authorization
        ↓
Authorization Integrity
        ↓
Sandbox Admission
        ↓
Execution Preparation
        ↓
Execution Attempt
        ↓
ToolService / ToolHandler
```

A caller using the guarded gateway cannot reach the underlying tool service
without crossing the existing gate.

## Consequences

JARVIS now has an explicit runtime-facing seam for real tool capabilities that
preserves the existing authority chain. Generic capability discovery remains
read-only, while invocation is structurally tied to the guarded execution
path. Request identity is preserved through explicit lineage fields rather
than relying on in-memory object identity across an execution handoff.

## Verification

Local verification passed:
- Focused M26.5 suite: 9/9 tests
- M26.3–M26.5 regression slice: 56/56 tests
- Full `src/core/tests` suite: 3156/3156 tests

The guarded gateway therefore satisfies the exact gate, request/result,
forwarding, denial, confirmation, lineage, and non-bypass contracts defined
above.
